# Video-Sharing Platform APIs (a mini YouTube)

> **Asked at:** Observe.AI, twice (the most likely question)
> - **Round 1 machine coding, Sep 2024:** 60 min of coding, then 30 min of high-level design questions.
>   The interviewer expected **Spring Boot APIs with request/response schemas and modular code**.
> - **SDE-3 machine coding, Oct 2024:** "Build a service like YouTube."
>
> **Language:** Java 17+ · **Package:** `org.videoSharingPlatform` · **Time:** ~90 min
> (Part 1 ≈ 40, Part 2 ≈ 20, Part 3 ≈ 30 of design talk). Everything lives in memory, no database.

## The problem (as the interviewer says it)

> "Build the backend APIs for a video-sharing platform. A user can save a video, fetch it, and watch it.
> Every watch adds a view. Then give me the top 10 most-viewed videos.
> You choose the HTTP methods, the paths and the parameters. Handle the edge cases and errors."

The interviewer is checking **API design** as much as the logic: the right HTTP method, the right status
code for each error, clean request/response schemas, and the usual layering
(`Controller → Service → Repository`, plus `model`).

> **No Spring in this repo?** Write the same layers in plain Java (`VideoController` with methods that
> take plain parameters and return the `Video`), and call them from `Main`.
> In the interview, use Spring Boot annotations (`@RestController`, `@PostMapping`, `@Valid`, `@ControllerAdvice`).

Finish **Part 1 completely** before you touch Part 2.

## Part 1: Must have (Round 1, Sep 2024, ~40 min)

### 1.1 The video

| Field         | Type      | Notes                                                              |
|---------------|-----------|--------------------------------------------------------------------|
| `videoId`     | `String`  | Generated by the server (UUID or a counter). Never sent by the client. |
| `uploaderId`  | `String`  | Who uploaded it. Required.                                         |
| `title`       | `String`  | Required, not blank, max 100 chars.                                |
| `description` | `String`  | Optional, max 5000 chars.                                          |
| `videoUrl`    | `String`  | Required. Must be a valid URL (see 1.3).                           |
| `uploadedAt`  | `Instant` | Set by the server when the video is saved.                         |
| `viewCount`   | `long`    | Starts at 0. Only ever goes up.                                    |

**Uniqueness:** the *Watch* API finds a video by `uploaderId + title`, so one uploader **cannot have two
videos with the same title**. A different uploader can reuse the title.

### 1.2 The three APIs

#### Save video

```http
POST /api/v1/videos
Content-Type: application/json

{
  "uploaderId": "u-42",
  "title": "Intro to LLD",
  "description": "Parking lot walkthrough",
  "videoUrl": "https://cdn.example.com/videos/intro-lld.mp4"
}
```

| Case                                                    | Status                     |
|---------------------------------------------------------|----------------------------|
| Saved                                                   | `201 Created` + `Location: /api/v1/videos/{videoId}` + the video body |
| Missing/blank `uploaderId`, `title` or `videoUrl`; too-long fields | `400 Bad Request`  |
| `videoUrl` is not a valid URL                           | `400 Bad Request`          |
| Same `uploaderId` already has a video with this `title` | `409 Conflict`             |

#### Fetch video

```http
GET /api/v1/videos?uploaderId=u-42&title=Intro%20to%20LLD
```

Returns the details, the **upload date** and the **current view count**. Fetching does **not** add a view.

```json
{
  "videoId": "7f3c...",
  "uploaderId": "u-42",
  "title": "Intro to LLD",
  "description": "Parking lot walkthrough",
  "videoUrl": "https://cdn.example.com/videos/intro-lld.mp4",
  "uploadedAt": "2024-09-14T10:15:30Z",
  "viewCount": 3
}
```

| Case                         | Status            |
|------------------------------|-------------------|
| Found                        | `200 OK`          |
| Missing query params         | `400 Bad Request` |
| No such video                | `404 Not Found`   |

#### Watch video

Takes **`uploaderId` and `title`** and adds **1** to the view count **on every call**.

```http
POST /api/v1/videos/watch
Content-Type: application/json

{ "uploaderId": "u-42", "title": "Intro to LLD" }
```

Returns the video with the updated `viewCount` (`200 OK`), or `404` / `400` like Fetch.

> Be ready to defend **why Watch is `POST`, not `GET`**: it changes state (the view count), so it is not
> safe or idempotent. A `GET` that writes can be fired twice by caches, prefetchers and retries.

### 1.3 URL validation

A `videoUrl` is valid when **all** of these hold:

1. It parses with `java.net.URI` (catch `URISyntaxException` → invalid).
2. The scheme is `http` or `https` (reject `ftp:`, `javascript:`, `file:`, no scheme).
3. It has a non-empty host.
4. It is at most 2048 characters.

```text
https://cdn.example.com/v/1.mp4        -> valid
http://example.com/watch?v=abc         -> valid
example.com/v.mp4                      -> invalid (no scheme)
ftp://example.com/v.mp4                -> invalid (scheme)
https://                               -> invalid (no host)
javascript:alert(1)                    -> invalid
""  /  null                            -> invalid (400, "videoUrl is required")
```

Put this in its own class (`VideoUrlValidator`) so it can be unit tested and swapped later
(e.g. "only allow our CDN domains").

### 1.4 Error response schema

Every error has the same shape. Don't leak stack traces.

```json
{
  "status": 409,
  "error": "CONFLICT",
  "message": "Uploader u-42 already has a video titled 'Intro to LLD'",
  "timestamp": "2024-09-14T10:15:31Z"
}
```

Throw domain exceptions from the service (`VideoNotFoundException`, `DuplicateVideoException`,
`InvalidVideoException`) and map them to status codes in **one place** (`@ControllerAdvice` /
a `GlobalExceptionHandler`), not with `if/else` in every controller method.

### 1.5 Walkthrough

```text
POST /videos      {u-42, "Intro to LLD", url=https://cdn.x.com/a.mp4}  -> 201, videoId=V1, viewCount=0
POST /videos      {u-42, "Intro to LLD", url=https://cdn.x.com/b.mp4}  -> 409 (same uploader + title)
POST /videos      {u-7,  "Intro to LLD", url=https://cdn.x.com/c.mp4}  -> 201, videoId=V2 (different uploader)
POST /videos      {u-42, "Bad URL",      url=cdn.x.com/a.mp4}          -> 400 (no scheme)
POST /videos      {u-42, "   ",          url=https://cdn.x.com/d.mp4}  -> 400 (blank title)

POST /videos/watch {u-42, "Intro to LLD"}   -> 200, viewCount=1
POST /videos/watch {u-42, "Intro to LLD"}   -> 200, viewCount=2
POST /videos/watch {u-42, "Nope"}           -> 404

GET  /videos?uploaderId=u-42&title=Intro to LLD  -> 200, viewCount=2, uploadedAt=...
GET  /videos?uploaderId=u-7&title=Intro to LLD   -> 200, viewCount=0 (V2 is untouched)
```

## Part 2: Should have (SDE-3, Oct 2024, ~20 min)

The SDE-3 version of the same question adds lookup by ID and a leaderboard.

### 2.1 Get video by ID

```http
GET /api/v1/videos/{videoId}      -> 200 with the video, or 404
```

### 2.2 Increment views by ID

```http
POST /api/v1/videos/{videoId}/views      -> 200 with the updated viewCount, or 404
```

Both Watch APIs (by `uploaderId + title` and by `videoId`) must go through the **same service method**,
so the counting logic exists once.

### 2.3 Top 10 most-viewed videos

```http
GET /api/v1/videos/top?limit=10
```

- Returns up to `limit` videos, **highest `viewCount` first**.
- Ties: the **earlier `uploadedAt`** goes first (then `videoId`, so the order is always deterministic).
- `limit` defaults to 10. `limit <= 0` or `limit > 100` → `400`.
- Fewer videos than `limit` → return all of them. No videos → `[]` (not 404).

```text
V1 views=5, V2 views=9, V3 views=5 (uploaded after V1), V4 views=0

GET /videos/top?limit=3  -> [V2 (9), V1 (5), V3 (5)]
```

Start with the simple version (sort all videos, take the first `limit`: O(n log n)), say its cost out loud,
then improve it (see the hints and follow-ups).

### 2.4 Concurrency on views

Many users watch the same video at the same time. Two concurrent watches must give **+2**, never +1.

```text
100 threads × 1000 watches each on V1  -> viewCount == 100000
```

Use `AtomicLong` (or `LongAdder`) for `viewCount` and `ConcurrentHashMap` for the store, and make
"check for duplicate title, then save" atomic (`putIfAbsent` / `computeIfAbsent` on the `uploaderId|title` key).

## Part 3: High-level design discussion (Round 1, last 30 min)

You won't code these. Talk through them with a quick diagram.

1. **Real uploads.** The client doesn't send a URL in real life; it uploads a file. Walk through it:
   pre-signed URL → object storage (S3) → upload-complete event → transcoding workers (several
   resolutions, HLS/DASH segments) → CDN. What is the video's status while it's processing?
2. **Storage.** Which database for video metadata and why? What are the partition key and the indexes
   (`videoId`, `(uploaderId, title)` unique)?
3. **View counting at scale.** A viral video gets 1M views/min. One row update per view will melt the DB.
   Options: buffer counts in Redis (`INCR`), batch-flush to the DB every few seconds, or send view events
   to Kafka and aggregate them. What does the user see: an exact or an approximate count?
4. **Top 10 at scale.** Redis sorted set (`ZINCRBY`, `ZREVRANGE 0 9`), or a stream job that keeps a
   top-K per time window. How do you do "top 10 **today**" or "**this week**"?
5. **Fake views.** How do you stop a script from calling Watch 10,000 times? (Count one view per
   user/session/IP per video per time window, rate limiting, minimum watch duration.)
6. **Read path.** Fetch is far more common than Save. Where do you cache, and how do you keep a cached
   `viewCount` from going stale?
7. **Idempotency.** A client retries Save after a timeout. How do you avoid a duplicate video?
   (`Idempotency-Key` header, or the `uploaderId + title` uniqueness you already have.)
8. **API evolution.** Why `/api/v1`? How would you add pagination to listing an uploader's videos
   (offset vs cursor)?

## Suggested structure

```text
org.videoSharingPlatform
├── Main.java                         // driver: calls the controller like HTTP requests would
├── controller/VideoController.java   // HTTP mapping only, no business logic
├── service/VideoService.java         // validation, uniqueness, view counting, top-K
├── repository/VideoRepository.java   // interface
├── repository/InMemoryVideoRepository.java
├── model/Video.java
├── validation/VideoUrlValidator.java
└── exception/  VideoNotFoundException, DuplicateVideoException, InvalidVideoException, GlobalExceptionHandler
```

The repository is an **interface** so the in-memory store can be swapped for a real DB without
touching the service.

## Required API (service layer)

```java
package org.videoSharingPlatform.service;

public class VideoService {
    public VideoService(VideoRepository videoRepository, VideoUrlValidator videoUrlValidator);

    // Part 1
    public Video saveVideo(String uploaderId, String title, String description, String videoUrl);
    public Video getVideo(String uploaderId, String title);          // throws VideoNotFoundException
    public Video watchVideo(String uploaderId, String title);        // +1 view

    // Part 2
    public Video getVideoById(String videoId);                       // throws VideoNotFoundException
    public Video watchVideoById(String videoId);                     // +1 view
    public List<Video> getMostViewedVideos(int limit);
}
```

## Example driver program

```java
package org.videoSharingPlatform;

public class Main {
    public static void main(String[] args) {
        VideoService videoService = new VideoService(new InMemoryVideoRepository(), new VideoUrlValidator());

        Video intro = videoService.saveVideo("u-42", "Intro to LLD", "Parking lot", "https://cdn.x.com/a.mp4");
        Video other = videoService.saveVideo("u-7",  "Intro to LLD", "",            "https://cdn.x.com/c.mp4");

        try {
            videoService.saveVideo("u-42", "Intro to LLD", "", "https://cdn.x.com/b.mp4");
        } catch (DuplicateVideoException e) {
            System.out.println("409: " + e.getMessage());
        }
        try {
            videoService.saveVideo("u-42", "Bad URL", "", "cdn.x.com/a.mp4");
        } catch (InvalidVideoException e) {
            System.out.println("400: " + e.getMessage());
        }

        videoService.watchVideo("u-42", "Intro to LLD");
        videoService.watchVideo("u-42", "Intro to LLD");
        System.out.println(videoService.getVideo("u-42", "Intro to LLD").getViewCount());   // 2

        videoService.watchVideoById(other.getVideoId());
        System.out.println(videoService.getVideoById(other.getVideoId()).getViewCount());   // 1

        System.out.println(videoService.getMostViewedVideos(10));   // [intro (2), other (1)]

        try {
            videoService.getVideoById("missing");
        } catch (VideoNotFoundException e) {
            System.out.println("404: " + e.getMessage());
        }
    }
}
```

## How you're judged

| # | Area                     | What a strong answer shows                                                          | Weight |
|---|--------------------------|--------------------------------------------------------------------------------------|--------|
| 1 | **API design**           | Correct methods (`POST` for writes, incl. Watch), clean paths, `201`/`400`/`404`/`409`, one error schema. | High |
| 2 | **Modularity**           | Controller / service / repository / exception separated; controller has no logic. | High |
| 3 | **Validation & edge cases** | URL rules, blank fields, duplicate title per uploader, unknown video, bad `limit`. | High   |
| 4 | **Correctness**          | Fetch doesn't count a view; Watch adds exactly 1; top-K order and tie-break are right. | High   |
| 5 | **Concurrency**          | Atomic view counts; no duplicate video under a race on Save.                        | Medium |
| 6 | **Design discussion**    | Upload pipeline, view counting at scale, top-K with Redis/streams, fake-view protection. | Medium |
| 7 | **Communication**        | Asks clarifying questions first and states assumptions.                             | Medium |

## Clarifying questions to ask before coding

1. What identifies a video for Watch: is `uploaderId + title` unique? *(Yes, per uploader.)*
2. Does Fetch count as a view? *(No, only Watch does.)*
3. Should repeat watches by the same user count? *(Yes in the base version, every call adds 1.)*
4. What makes a URL valid: any http(s) URL, or only our domains? *(Any http/https URL with a host.)*
5. Is `description` optional? *(Yes.)*
6. Is a database expected, or is in-memory fine? *(In-memory, behind a repository interface.)*
7. For top 10: all-time, or within a time window? *(All-time for now.)*

---

## Follow-up questions

1. What is the cost of `getMostViewedVideos` in your design? How would you make it O(k) or O(log n) per view?
2. How do you make "check the title is free, then save" safe when two requests arrive at once?
3. Why is `viewCount` a `long` and not an `int`?
4. If titles can be edited, what breaks in the Watch-by-title API? Why is `videoId` a better key?
5. How would you add delete or unlist? What should Fetch, Watch and Top 10 return for a deleted video?
6. How would you test the controller and the service separately?

## Hints

<details>
<summary>Hint 1: two maps in the repository</summary>

```java
Map<String, Video> videosById = new ConcurrentHashMap<>();
Map<String, String> videoIdByUploaderAndTitle = new ConcurrentHashMap<>();   // key: uploaderId + "|" + title
```
Fetch and Watch by title are O(1): look up the id, then the video.
</details>

<details>
<summary>Hint 2: atomic save</summary>

```java
String existingId = videoIdByUploaderAndTitle.putIfAbsent(key, video.getVideoId());
if (existingId != null) throw new DuplicateVideoException(...);
videosById.put(video.getVideoId(), video);
```
`putIfAbsent` makes the check and the insert one atomic step, so two racing saves can't both win.
</details>

<details>
<summary>Hint 3: URL validator</summary>

```java
public boolean isValid(String videoUrl) {
    if (videoUrl == null || videoUrl.isBlank() || videoUrl.length() > 2048) return false;
    try {
        URI uri = new URI(videoUrl);
        String scheme = uri.getScheme();
        boolean isHttp = "http".equalsIgnoreCase(scheme) || "https".equalsIgnoreCase(scheme);
        return isHttp && uri.getHost() != null && !uri.getHost().isBlank();
    } catch (URISyntaxException e) {
        return false;
    }
}
```
</details>

<details>
<summary>Hint 4: one comparator for top 10</summary>

```java
Comparator<Video> mostViewedFirst = Comparator
        .comparingLong(Video::getViewCount).reversed()
        .thenComparing(Video::getUploadedAt)
        .thenComparing(Video::getVideoId);
```
Simple version: `videosById.values().stream().sorted(mostViewedFirst).limit(limit).toList()`.
Better when n is large: a min-heap of size `limit` while scanning, O(n log k).
Best for frequent reads: keep a `TreeSet` ordered by the comparator and remove → update → re-add on each view
(the same "a priority structure doesn't re-sort a changed element" trap as the stock exchange question).
</details>

<details>
<summary>Hint 5: map exceptions in one place</summary>

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(VideoNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(VideoNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(ErrorResponse.of(404, "NOT_FOUND", e.getMessage()));
    }
    // DuplicateVideoException -> 409, InvalidVideoException / MethodArgumentNotValidException -> 400
}
```
</details>
